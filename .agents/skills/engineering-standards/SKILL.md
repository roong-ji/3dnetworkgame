# 소프트웨어 공학 표준 및 클린 코드 지침 (Clean Code & Engineering Standards)

## 1. 객체 지향 및 SOLID 원칙 명확화
- **SRP (단일 책임 원칙)**: 클래스와 모듈은 단 하나의 역할과 '변경해야 할 이유'를 가져야 한다. 여러 책임을 가진 God Class 작성을 엄격히 경계한다.
- **OCP (개방-폐쇄 원칙)**: 기능 추가에는 열려 있고(확장성), 기존 코드 수정에는 닫혀 있어야 한다. `if/switch` 문 남용 대신 다형성(Interface, Abstract Class)을 활용한다.
- **LSP (리스코프 치환 원칙)**: 자식 클래스는 부모 클래스의 동작을 깨뜨리지 않고 언제나 교체될 수 있어야 한다.
- **ISP (인터페이스 분리 원칙)**: 인터페이스는 클라이언트가 필요로 하는 메서드만 갖도록 작게 분리(Segregation)한다. 하나의 거대한 인터페이스보다 목적에 맞는 여러 개의 작은 인터페이스가 낫다.
- **DIP (의존성 역전 원칙)**: 상위 모듈이 하위 모듈의 구체적인 구현에 직접 의존해선 안 되며, 둘 다 '추상화(Interface)'에 의존해야 한다.

## 2. 아키텍처 규칙 (Clean Architecture & DDD)
- **의존성의 방향 (Dependency Rule)**: 의존성은 항상 외부 계층(프레임워크, DB, UI)에서 내부 계층(핵심 도메인 로직)으로 향해야 한다. 핵심 로직은 Unity 엔진의 변경에 영향을 받지 않는 순수 C# 코드로 구성하는 것을 지향한다.
- **캡슐화 및 상태 관리**: 객체의 내부 상태(Data)는 외부에서 함부로 직접 수정할 수 없도록 접근 제어자(`private set` 등)로 강하게 보호하고, 의미 있는 비즈니스 메서드를 통해서만 상태를 변경한다.
- **의존성 주입 (Dependency Injection)**: 강결합의 주범인 전역 `Singleton` 패턴의 남용을 지양한다. 객체 생성과 사용을 분리하고, 생성자나 DI 프레임워크를 통해 의존성을 외부에서 주입받아 모듈 간 결합도를 낮추고 단위 테스트(Unit Test)를 가능하게 만든다.

## 3. 유니티 최적화 및 구조화 설계 (Unity Specific)
- **MonoBehaviour 의존성 최소화**: `MonoBehaviour`는 가급적 뷰(View) 역할과 유니티 생명주기(Life Cycle) 이벤트 연결에만 국한시키고, 주요 로직(Model/Presenter)은 분리한다. (MVP 패턴의 뷰-로직 분리 패턴 권장)
- **No Heavy Operations in Update**: 매 프레임 호출되는 `Update()`, `FixedUpdate()` 내부에서 가장 많은 자원을 소모하는 `GetComponent<T>()`, `GameObject.Find()`, `Instantiate()` 등의 함수 호출을 절대 금지한다. 상단의 `Awake()`나 `Start()`에서 미리 캐싱(Caching)해 참조를 사용한다.
- **Memory & GC 스파이크 방지**: 가비지 컬렉터(GC)에 의한 프레임 드랍을 막기 위해 런타임 중 계속되는 메모리 할당과 해제를 피한다. 잦은 객체 생성/파괴는 객체 풀링(Object Pool)을 활용하고, 데이터 전송이나 임시 연산용 객체는 가비지가 생기지 않는 구조체(`struct`)를 적극 고려한다.
- **객체 캐싱(Caching)**: `new WaitForSeconds()`와 같이 반복적으로 사용되며 힙(Heap)에 할당되는 객체는 미리 멤버 변수에 생성해 두고 재사용한다.

## 4. 코드 작성 스타일 (Clean Code Practices)
- **의도를 드러내는 이름**: 변수, 함수, 클래스명은 의미를 알 수 없는 줄임말이나 애매한 단어를 피하고 그 역할과 의도를 명확하게 알 수 있도록 짓는다. (예: `mgr` ❌ -> `Manager` ⭕)
- **작은 함수 (Small Functions)**: 메서드는 "한 가지 역할만" 수행해야 하며 가급적 짧게 가져간다. 하나의 메서드가 20줄을 넘지 않도록 나누고, `if-else` 중첩 등 들여쓰기(Indent) 깊이가 2단계를 넘지 않도록 리팩터링한다. (Early Return 패턴 적극 활용)
- **매개변수 최소화**: 함수의 인수 개수는 0~2개가 좋으며, 가급적 3개를 넘지 않도록 한다. 파라미터가 많아진다면 관련된 변수들을 응집도 있는 객체로 묶어 전달한다.
- **주석 (Comments) 규칙**: 나쁘거나 이해하기 힘든 코드를 설명하기 위해 주석을 쓰지 않는다. 변수/함수명 변경이나 메서드 추출 등 "코드 그 자체"가 문서를 대신하도록 로직을 정리한다. 주석은 API 문서나, 비즈니스상 어쩔 수 없이 추가된 예외 상황을 설명할 때만 제한적으로 사용한다.
